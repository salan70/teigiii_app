## レビューチェックリスト

**コード品質:**
- 関心の分離が適切か？
- エラーハンドリングは適切か？
- 型安全性は確保されているか（該当する場合）？
- DRY 原則に従っているか？
- エッジケースは処理されているか？

**アーキテクチャ:**
- 設計判断は妥当か？
- スケーラビリティは考慮されているか？
- パフォーマンスへの影響は？
- セキュリティの懸念は？

**テスト:**
- テストがロジックを実際にテストしているか（モックではなく）？
- エッジケースはカバーされているか？
- 必要な箇所に統合テストがあるか？
- すべてのテストがパスしているか？

**要件:**
- 計画の要件をすべて満たしているか？
- 実装が仕様に合致しているか？
- スコープクリープはないか？
- 破壊的変更は文書化されているか？

**本番リリース準備:**
- マイグレーション戦略（スキーマ変更がある場合）？
- 後方互換性は考慮されているか？
- ドキュメントは完全か？
- 明らかなバグはないか？

## 重要なルール

**すべきこと:**
- 実際の深刻度で分類する（すべてが重大ではない）
- 具体的に指摘する（ファイル名:行番号、曖昧にしない）
- なぜ問題なのか説明する
- 長所を認める
- 明確な判定を出す

**してはいけないこと:**
- 確認せずに「良さそう」と言う
- 些細な指摘を重大として扱う
- レビューしていないコードにフィードバックする
- 曖昧にする（「エラーハンドリングを改善」）
- 明確な判定を避ける

#### 軽微
1. **進捗表示**
   - ファイル: indexer.ts:130

**根拠:** コア実装は堅実でアーキテクチャとテストが良好。重要な問題（ヘルプテキスト、日付バリデーション）は容易に修正可能で、コア機能には影響しない。
