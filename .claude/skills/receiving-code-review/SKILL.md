# コードレビューの受け方

## 概要

コードレビューには技術的な評価が必要であり、感情的なパフォーマンスは不要。

**基本原則:** 実装前に検証する。仮定の前に質問する。社会的な快適さより技術的な正しさ。

## 対応パターン

```
コードレビューのフィードバックを受けたら:

1. 読む: フィードバック全体を反応せずに読む
2. 理解する: 要件を自分の言葉で言い換える（または質問する）
3. 検証する: コードベースの実態と照合する
4. 評価する: このコードベースに対して技術的に妥当か？
5. 応答する: 技術的な確認、または根拠ある反論
6. 実装する: 1項目ずつ、各項目をテスト
```

## 禁止される応答

**絶対にしないこと:**
- 「おっしゃる通りです！」（明示的な CLAUDE.md 違反）
- 「良い指摘です！」 /「素晴らしいフィードバック！」（形式的）
- 「すぐに実装します」（検証前に）

**代わりに:**
- 技術的な要件を言い換える
- 明確化のための質問をする
- 間違っている場合は技術的な根拠で反論する
- 作業に取り掛かる（言葉より行動）

## 不明確なフィードバックの処理

```
いずれかの項目が不明確な場合:
  止まる - まだ何も実装しない
  不明確な項目について明確化を求める

理由: 項目同士が関連している可能性がある。部分的な理解 = 誤った実装。
```

**例:**
```
人間のパートナー: 「1-6 を修正して」
1,2,3,6 は理解。4,5 が不明確。

❌ 間違い: 1,2,3,6 を今実装、4,5 は後で聞く
✅ 正解: 「1,2,3,6 は理解しました。4 と 5 について明確化が必要です。」
```

## ソース別の対応

### 人間のパートナーから
- **信頼する** — 理解した後に実装
- **スコープが不明確なら質問する**
- **形式的な同意はしない**
- **行動に移すか、技術的な確認のみ**

### 外部レビューアーから
```
実装前に:
  1. 確認: このコードベースに対して技術的に正しいか？
  2. 確認: 既存の機能を壊さないか？
  3. 確認: 現在の実装の理由は？
  4. 確認: すべてのプラットフォーム/バージョンで動作するか？
  5. 確認: レビューアーは完全なコンテキストを理解しているか？

提案が間違っていると思われる場合:
  技術的な根拠で反論する

簡単に検証できない場合:
  「[X] なしでは検証できません。[調査/質問/続行] しますか？」と伝える

人間のパートナーの過去の判断と矛盾する場合:
  まず人間のパートナーと相談する
```

**人間のパートナーのルール:** 「外部フィードバック — 懐疑的に、でも慎重に確認する」

### 「プロフェッショナルな」機能に対する YAGNI チェック

```
レビューアーが「適切に実装する」ことを提案した場合:
  コードベースで実際の使用箇所を grep する

  未使用の場合: 「このエンドポイントは呼ばれていません。削除（YAGNI）しますか？」
  使用されている場合: 適切に実装する
```

**人間のパートナーのルール:** 「あなたとレビューアーは両方とも私に報告する。この機能が不要なら、追加しない。」

## 実装順序

```
複数項目のフィードバック:
  1. 不明確なものをまず明確化
  2. 次にこの順序で実装:
     - ブロッキングの問題（壊れている、セキュリティ）
     - 単純な修正（タイポ、インポート）
     - 複雑な修正（リファクタリング、ロジック）
  3. 各修正を個別にテスト
  4. リグレッションがないことを検証
```

## いつ反論すべきか

反論する場合:
- 提案が既存機能を壊す
- レビューアーが完全なコンテキストを把握していない
- YAGNI に違反（未使用の機能）
- このスタックに対して技術的に不正確
- レガシー/互換性の理由がある
- 人間のパートナーのアーキテクチャ判断と矛盾

**反論の方法:**
- 防御的ではなく技術的な根拠を使う
- 具体的な質問をする
- 動作するテスト/コードを参照する
- アーキテクチャに関わる場合は人間のパートナーを巻き込む

**声に出して反論しにくい場合のシグナル:** "Strange things are afoot at the Circle K"

## 正しいフィードバックを認める

フィードバックが正しい場合:
```
✅ 「修正しました。[変更内容の簡潔な説明]」
✅ 「発見ありがとうございます — [具体的な問題]。[場所]で修正しました。」
✅ [修正してコードで示す]

❌ 「おっしゃる通りです！」
❌ 「良い指摘です！」
❌ 「ご指摘ありがとうございます！」
❌ 「[何かに]感謝します」
❌ いかなる感謝の表現
```

**なぜ感謝しないか:** 行動が語る。修正するだけ。コード自体がフィードバックを聞いたことを示す。

**「ありがとう」と書こうとしている自分に気づいたら:** 削除する。代わりに修正内容を述べる。

## 反論が間違っていた場合の訂正

反論して間違っていた場合:
```
✅ 「正しかったです — [X] を確認したところ [Y] でした。実装します。」
✅ 「検証しましたが正しいです。[理由]で最初の理解が間違っていました。修正します。」

❌ 長い謝罪
❌ なぜ反論したかの弁解
❌ 過度な説明
```

訂正を事実として述べ、先に進む。

## よくある間違い

| 間違い | 修正 |
|---------|-----|
| 形式的な同意 | 要件を述べるか、行動で示す |
| 盲目的な実装 | コードベースの実態と照合する |
| テストなしのバッチ実装 | 1つずつ、各項目をテスト |
| レビューアーが正しいと仮定 | 壊れないか確認する |
| 反論を避ける | 技術的な正しさ > 快適さ |
| 部分的な実装 | まず全項目を明確化する |
| 検証できないまま続行 | 制限を述べ、方向性を聞く |

## 実例

**形式的な同意（悪い例）:**
```
レビューアー: 「レガシーコードを削除して」
❌ 「おっしゃる通りです！削除します...」
```

**技術的な検証（良い例）:**
```
レビューアー: 「レガシーコードを削除して」
✅ 「確認中... ビルドターゲットは 10.15+ で、この API は 13+ が必要です。後方互換性のためにレガシーが必要です。バンドル ID が間違っているので、修正するか pre-13 サポートを廃止するかどちらにしますか？」
```

**YAGNI（良い例）:**
```
レビューアー: 「DB、日付フィルター、CSV エクスポート付きの適切なメトリクストラッキングを実装して」
✅ 「コードベースを grep しましたが、このエンドポイントを呼んでいるものはありません。削除（YAGNI）しますか？それとも見落としている使用箇所がありますか？」
```

**不明確な項目（良い例）:**
```
人間のパートナー: 「項目 1-6 を修正して」
1,2,3,6 は理解。4,5 が不明確。
✅ 「1,2,3,6 は理解しました。実装前に 4 と 5 について明確化が必要です。」
```

## GitHub スレッドへの返信

GitHub のインラインレビューコメントに返信する場合、トップレベルの PR コメントではなく、コメントスレッド内で返信する。

**全スレッド対応の原則:**
- すべてのレビューコメントスレッドに返信すること（未返信のスレッドを残さない）
- 修正した場合: 修正内容を簡潔に述べて Resolve する
- 反論する場合: 技術的根拠を述べる（Resolve しない — レビューアーの確認を待つ）
- 質問・議論の場合: 回答または質問を返す（Resolve しない）

### スレッド返信コマンド

```bash
# インラインレビューコメントへのスレッド返信（REST API）
gh api repos/{owner}/{repo}/pulls/{pr}/comments/{comment_id}/replies \
  -f body="修正内容の説明"
```

### スレッド Resolve コマンド

GitHub REST API にはスレッド Resolve のエンドポイントがない。GraphQL API を使う。

```bash
# Step 1: PR のレビュースレッドを取得し、スレッド ID を特定する
gh api graphql -f query='
  query($owner: String!, $repo: String!, $pr: Int!) {
    repository(owner: $owner, name: $repo) {
      pullRequest(number: $pr) {
        reviewThreads(first: 100) {
          nodes {
            id
            isResolved
            comments(first: 1) {
              nodes {
                id
                databaseId
                body
              }
            }
          }
        }
      }
    }
  }
' -f owner='{owner}' -f repo='{repo}' -F pr='{pr_number}'

# Step 2: 対象スレッドの node ID で Resolve する
gh api graphql -f query='
  mutation($threadId: ID!) {
    resolveReviewThread(input: { threadId: $threadId }) {
      thread { isResolved }
    }
  }
' -f threadId='{thread_node_id}'
```

### 対応フロー

1. `gh api repos/{owner}/{repo}/pulls/{pr}/comments` でレビューコメント一覧を取得
2. 各コメントに対しスレッド返信（REST API）
3. 修正済みのスレッドは GraphQL で Resolve（返信と Resolve はセットで行う）
4. 反論・質問のスレッドは Resolve しない（レビューアーの確認を待つ）

## 結論

**外部フィードバック = 従うべき命令ではなく、評価すべき提案。**

検証する。質問する。そして実装する。

形式的な同意は不要。常に技術的な厳密さを。
