# アイデアを設計に仕上げるブレインストーミング

すべてのタスクはこのスキルから始まる。ユーザーが「brainstorming 不要」と明示した場合のみ例外。

自然な対話を通じて、アイデアを完成した設計・仕様に仕上げます。

まずプロジェクトの現状を把握し、一度にひとつずつ質問してアイデアを洗練させます。何を構築するか理解できたら、設計を提示してユーザーの承認を得ます。

<HARD-GATE>
設計を提示してユーザーが承認するまで、実装スキルの呼び出し、コードの記述、プロジェクトのスキャフォールディング、その他の実装アクションを行ってはなりません。どんなに単純に見えるプロジェクトでも例外はありません。
</HARD-GATE>

## アンチパターン: 「設計するほどでもない」

すべてのプロジェクトがこのプロセスを経ます。TODO リスト、単一関数のユーティリティ、設定変更 — すべてです。「単純な」プロジェクトこそ、検討不足の前提が最も多くの手戻りを生みます。本当に単純なプロジェクトなら設計は数行で済みますが、必ず提示して承認を得てください。

## チェックリスト

以下の項目ごとにタスクを作成し、順番に完了させてください:

1. **プロジェクトの文脈を把握** — ファイル、ドキュメント、最近のコミットを確認
2. **ビジュアルコンパニオンを提案** (ビジュアルに関する質問が予想される場合) — 単独のメッセージとして送信し、確認質問と混ぜない。詳細は下記のビジュアルコンパニオンセクションを参照。
3. **確認質問** — 一度にひとつずつ、目的・制約・成功基準を理解する
4. **2〜3 のアプローチを提案** — トレードオフと推奨を示す
5. **設計を提示** — 複雑さに応じたセクション構成で、各セクション後にユーザーの承認を得る
6. **設計ドキュメントを作成** — `doc/specs/YYYY-MM-DD-<topic>-design.md` に保存してコミット
7. **仕様レビューループ** — spec-document-reviewer サブエージェントを的確なレビュー文脈でディスパッチ（セッション履歴は渡さない）。問題があれば修正して再ディスパッチ、承認されるまで繰り返す（最大 3 回、超過したらユーザーに報告）
8. **ユーザーが仕様を確認** — 続行前にユーザーに仕様ファイルのレビューを依頼
9. **実装への移行** — wf-03-writing-plans スキルを呼び出して実装計画を作成

## プロセス

**アイデアの理解:**

- まずプロジェクトの現状を確認（ファイル、ドキュメント、最近のコミット）
- 詳細な質問の前にスコープを評価: リクエストが複数の独立したサブシステムを含む場合（例: 「チャット、ファイルストレージ、課金、分析を備えたプラットフォームを構築」）、すぐにその旨を指摘する。分解が必要なプロジェクトの詳細を掘り下げるのに質問を費やさない。
- プロジェクトが単一仕様に収まらないほど大きい場合、サブプロジェクトへの分解を支援する: 独立した部分は何か、どう関連するか、どの順序で構築すべきか。その後、最初のサブプロジェクトを通常の設計フローでブレストする。各サブプロジェクトはそれぞれ独自の仕様 → 計画 → 実装サイクルを持つ。
- 適切なスコープのプロジェクトでは、一度にひとつずつ質問してアイデアを洗練する
- 可能な限り選択式の質問を使うが、自由回答でも構わない
- 1 メッセージにつき質問はひとつだけ — トピックをさらに掘り下げる必要がある場合は複数のメッセージに分ける
- 目的、制約、成功基準の理解に集中する

**アプローチの探索:**

- トレードオフを示した 2〜3 の異なるアプローチを提案する
- 推奨とその理由を添えて会話形式で選択肢を提示する
- 推奨オプションを先に示し、その理由を説明する

**設計の提示:**

- 何を構築するか理解できたら、設計を提示する
- 各セクションの長さは複雑さに応じて調整: 簡単なら数行、複雑なら 200〜300 語程度
- 各セクション後に「ここまで問題ないか」を確認する
- 対象: アーキテクチャ、コンポーネント、データフロー、エラーハンドリング、テスト
- 何かが合わない場合は戻って確認する柔軟性を持つ

**分離と明確性のための設計:**

- システムをより小さな単位に分割する。各単位はひとつの明確な目的を持ち、明確に定義されたインターフェースで通信し、独立して理解・テストできるようにする
- 各単位について「何をするか」「どう使うか」「何に依存するか」を答えられるべき
- 内部を読まなくても単位の機能を理解できるか？内部を変更しても利用者を壊さないか？そうでなければ境界の見直しが必要
- 小さくて境界が明確な単位は作業もしやすい — コンテキストに収まるコードの方が的確に推論でき、ファイルが集中的であるほど編集の信頼性が高まる。ファイルが大きくなったら、それは責務過多のサインであることが多い

**既存コードベースでの作業:**

- 変更を提案する前に既存の構造を調べる。既存のパターンに従う。
- 既存コードに作業に影響する問題がある場合（例: 肥大化したファイル、不明確な境界、絡み合った責務）、設計の一部として的を絞った改善を含める — 優秀な開発者が作業中のコードを改善するのと同じように。
- 無関係なリファクタリングは提案しない。現在の目標に資することに集中する。

## 設計の後

**ドキュメント化:**

- 検証済みの設計（仕様）を `doc/specs/YYYY-MM-DD-<topic>-design.md` に書き出す
  - （仕様の保存場所についてユーザーの指定がある場合はそちらを優先）
- elements-of-style:writing-clearly-and-concisely スキルがあれば使用
- 設計ドキュメントを Git にコミット

**仕様レビューループ:**
仕様ドキュメントを書いた後:

1. spec-document-reviewer サブエージェントをディスパッチ（spec-document-reviewer-prompt.md を参照）
2. 問題が見つかった場合: 修正し、再ディスパッチ。承認されるまで繰り返す
3. ループが 3 回を超えた場合、ユーザーに報告して判断を仰ぐ

**ユーザーレビューゲート:**
仕様レビューループ通過後、続行前にユーザーに仕様のレビューを依頼する:

> 「仕様を作成し `<path>` にコミットしました。実装計画の作成に進む前に、内容を確認して変更があればお知らせください。」

ユーザーの回答を待つ。変更が要求された場合は修正して仕様レビューループを再実行する。ユーザーが承認してから次に進む。

**実装:**

- **Skill ツールを使って** `wf-03-writing-plans` スキルを invoke し、詳細な実装計画を作成する
- 他のスキルは呼び出さないこと。wf-03-writing-plans が次のステップ。
- スキルの内容を手動で再現せず、必ず Skill ツール経由で呼び出すこと。

## 基本原則

- **一度にひとつの質問** — 複数の質問で圧倒しない
- **選択式を優先** — 可能であれば自由回答より答えやすい
- **YAGNI を徹底** — 不要な機能はすべての設計から排除
- **代替案を探索** — 決定前に必ず 2〜3 のアプローチを提案
- **段階的な検証** — 設計を提示し、承認を得てから次に進む
- **柔軟に対応** — 何かが合わないときは戻って確認

## ビジュアルコンパニオン

ブレインストーミング中にモックアップ、図、ビジュアルオプションを表示するためのブラウザベースのコンパニオンツール。モードではなくツールとして利用可能。コンパニオンの使用に同意するということは、ビジュアルで説明した方がよい質問に使えるということであり、すべての質問がブラウザを経由するわけではありません。

**コンパニオンの提案:** 今後の質問にビジュアルコンテンツ（モックアップ、レイアウト、図）が含まれると予想される場合、同意を得るために一度だけ提案します:
> 「これから議論する内容には、ウェブブラウザで見せた方がわかりやすいものがあるかもしれません。進行に合わせて、モックアップ、図、比較、その他のビジュアルを作成できます。この機能はまだ新しく、トークン消費が多めです。試してみますか？（ローカル URL を開く必要があります）」

**この提案は単独のメッセージでなければなりません。** 確認質問、文脈の要約、その他の内容と組み合わせないでください。メッセージには上記の提案のみを含め、他は何も入れません。ユーザーの回答を待ってから続行してください。辞退された場合はテキストのみのブレインストーミングで進めます。

**質問ごとの判断:** ユーザーが同意した後でも、各質問ごとにブラウザかターミナルかを判断します。基準: **見た方が読むより理解しやすいか？**

- **ブラウザを使用** — モックアップ、ワイヤーフレーム、レイアウト比較、アーキテクチャ図、ビジュアルデザインの並列比較など、それ自体がビジュアルなコンテンツ
- **ターミナルを使用** — 要件の質問、概念的な選択、トレードオフリスト、A/B/C/D のテキストオプション、スコープの判断など、テキストベースのコンテンツ

UI に関する質問が自動的にビジュアルの質問になるわけではありません。「この文脈でパーソナリティとは何を意味するか？」は概念的な質問 — ターミナルを使用。「どちらのウィザードレイアウトがいいか？」はビジュアルの質問 — ブラウザを使用。

同意が得られた場合、続行前に詳細ガイドを読んでください:
`skills/wf-01-brainstorming/visual-companion.md`
