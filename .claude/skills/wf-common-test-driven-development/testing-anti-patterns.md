# テストのアンチパターン

**このリファレンスを読むタイミング:** テストの作成や変更、モックの追加、プロダクションコードにテスト専用メソッドを追加したくなったとき。

## 概要

テストは実際の振る舞いを検証しなければならない。モックの振る舞いではない。モックは分離のための手段であり、テスト対象ではない。

**基本原則:** コードが何をするかをテストする。モックが何をするかではない。

**厳格な TDD に従えばこれらのアンチパターンは防止できる。**

## 鉄の掟

```
1. モックの振る舞いを絶対にテストしない
2. プロダクションクラスにテスト専用メソッドを絶対に追加しない
3. 依存関係を理解せずにモックを絶対にしない
```

## アンチパターン 1: モックの振る舞いをテストする

**違反:**
```typescript
// ❌ 悪い例: モックの存在をテストしている
test('サイドバーを描画する', () => {
  render(<Page />);
  expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
});
```

**なぜ問題か:**
- コンポーネントではなくモックが動作するかを検証している
- モックがあればテストがパス、なければ失敗
- 実際の振る舞いについて何もわからない

**人間のパートナーの指摘:** 「これはモックの振る舞いをテストしていないか？」

**修正:**
```typescript
// ✅ 良い例: 実際のコンポーネントをテストするか、モックしない
test('サイドバーを描画する', () => {
  render(<Page />);  // サイドバーをモックしない
  expect(screen.getByRole('navigation')).toBeInTheDocument();
});

// または分離のためにサイドバーをモックする必要がある場合:
// モックに対してアサートしない — サイドバーが存在する状態での Page の振る舞いをテストする
```

### ゲート関数

```
モック要素に対してアサートする前に:
  問う: 「実際のコンポーネントの振る舞いをテストしているか、
        それともモックの存在をテストしているか？」

  モックの存在をテストしている場合:
    止まる - アサーションを削除するか、コンポーネントのモックを解除する

  代わりに実際の振る舞いをテストする
```

## アンチパターン 2: プロダクションにテスト専用メソッド

**違反:**
```typescript
// ❌ 悪い例: destroy() はテストでしか使われない
class Session {
  async destroy() {  // プロダクション API に見える！
    await this._workspaceManager?.destroyWorkspace(this.id);
    // ... クリーンアップ
  }
}

// テスト内で
afterEach(() => session.destroy());
```

**なぜ問題か:**
- プロダクションクラスがテスト専用コードで汚染される
- プロダクションで誤って呼ばれると危険
- YAGNI と関心の分離に違反
- オブジェクトのライフサイクルとエンティティのライフサイクルを混同

**修正:**
```typescript
// ✅ 良い例: テストユーティリティがテストのクリーンアップを処理
// Session に destroy() はない — プロダクションではステートレス

// test-utils/ 内で
export async function cleanupSession(session: Session) {
  const workspace = session.getWorkspaceInfo();
  if (workspace) {
    await workspaceManager.destroyWorkspace(workspace.id);
  }
}

// テスト内で
afterEach(() => cleanupSession(session));
```

### ゲート関数

```
プロダクションクラスにメソッドを追加する前に:
  問う: 「これはテストでしか使わないか？」

  はいの場合:
    止まる - 追加しない
    代わりにテストユーティリティに置く

  問う: 「このクラスはこのリソースのライフサイクルを所有しているか？」

  いいえの場合:
    止まる - このメソッドにはこのクラスは不適切
```

## アンチパターン 3: 理解せずにモックする

**違反:**
```typescript
// ❌ 悪い例: モックがテストロジックを壊す
test('重複サーバーを検出する', () => {
  // テストが依存する設定書き込みをモックが阻止！
  vi.mock('ToolCatalog', () => ({
    discoverAndCacheTools: vi.fn().mockResolvedValue(undefined)
  }));

  await addServer(config);
  await addServer(config);  // エラーになるべき — でもならない！
});
```

**なぜ問題か:**
- モックされたメソッドにテストが依存する副作用があった（設定書き込み）
- 「安全のため」の過剰モックが実際の振る舞いを壊す
- 誤った理由でテストがパスまたは不可解に失敗

**修正:**
```typescript
// ✅ 良い例: 適切なレベルでモック
test('重複サーバーを検出する', () => {
  // 遅い部分だけモック、テストに必要な振る舞いは保持
  vi.mock('MCPServerManager'); // 遅いサーバー起動だけモック

  await addServer(config);  // 設定が書き込まれる
  await addServer(config);  // 重複検出 ✓
});
```

### ゲート関数

```
メソッドをモックする前に:
  止まる - まだモックしない

  1. 問う: 「実際のメソッドにはどんな副作用があるか？」
  2. 問う: 「テストはそれらの副作用に依存しているか？」
  3. 問う: 「このテストに何が必要か完全に理解しているか？」

  副作用に依存している場合:
    より低いレベルでモック（実際の遅い/外部操作）
    または必要な振る舞いを保持するテストダブルを使う
    テストが依存する高レベルメソッドをモックしない

  テストが何に依存しているか不明な場合:
    まず実際の実装でテストを実行
    何が起きる必要があるか観察
    その後、適切なレベルで最小限のモックを追加

  危険信号:
    - 「安全のためにモックしよう」
    - 「遅いかもしれないからモックしよう」
    - 依存チェーンを理解せずにモック
```

## アンチパターン 4: 不完全なモック

**違反:**
```typescript
// ❌ 悪い例: 部分的なモック — 必要と思うフィールドだけ
const mockResponse = {
  status: 'success',
  data: { userId: '123', name: 'Alice' }
  // 欠落: 下流のコードが使用する metadata
};

// 後で: コードが response.metadata.requestId にアクセスして壊れる
```

**なぜ問題か:**
- **部分的なモックが構造上の仮定を隠す** — 知っているフィールドだけモックしている
- **下流のコードが含めなかったフィールドに依存する可能性** — サイレントな失敗
- **テストはパスするが統合で失敗** — モック不完全、実 API 完全
- **偽の信頼** — テストが実際の振る舞いについて何も証明しない

**鉄の掟:** 直近のテストが使うフィールドだけでなく、現実に存在する完全なデータ構造をモックすること。

**修正:**
```typescript
// ✅ 良い例: 実際の API の完全性を反映
const mockResponse = {
  status: 'success',
  data: { userId: '123', name: 'Alice' },
  metadata: { requestId: 'req-789', timestamp: 1234567890 }
  // 実際の API が返すすべてのフィールド
};
```

### ゲート関数

```
モックレスポンスを作成する前に:
  確認: 「実際の API レスポンスにはどのフィールドが含まれるか？」

  アクション:
    1. ドキュメント/サンプルから実際の API レスポンスを確認
    2. 下流でシステムが消費する可能性のあるすべてのフィールドを含める
    3. モックが実際のレスポンススキーマと完全に一致することを検証

  重要:
    モックを作成するなら、構造全体を理解する必要がある
    部分的なモックは、省略したフィールドにコードが依存するとサイレントに失敗する

  不確かな場合: ドキュメントに記載されたすべてのフィールドを含める
```

## アンチパターン 5: 後付けの統合テスト

**違反:**
```
✅ 実装完了
❌ テスト未作成
「テスト準備完了」
```

**なぜ問題か:**
- テストは実装の一部であり、オプションのフォローアップではない
- TDD に従えばこれは起こらない
- テストなしに完了を主張できない

**修正:**
```
TDD サイクル:
1. 失敗するテストを書く
2. パスするように実装
3. リファクタ
4. それから完了を主張
```

## モックが複雑になりすぎたとき

**警告サイン:**
- モックのセットアップがテストロジックより長い
- テストをパスさせるためにすべてをモック
- モックに実際のコンポーネントが持つメソッドが欠けている
- モックを変更するとテストが壊れる

**人間のパートナーの質問:** 「ここでモックを使う必要があるのか？」

**検討:** 複雑なモックより実際のコンポーネントを使った統合テストの方がシンプルなことが多い

## TDD がこれらのアンチパターンを防ぐ理由

**なぜ TDD が助けになるか:**
1. **テストを先に書く** → 実際に何をテストしているか考えることを強制
2. **失敗を確認する** → テストがモックではなく実際の振る舞いをテストしていることを確認
3. **最小限の実装** → テスト専用メソッドが入り込まない
4. **実際の依存関係** → モックする前にテストが実際に何を必要としているか見える

**モックの振る舞いをテストしているなら、TDD に違反している** — 実際のコードに対してテストを失敗させずにモックを追加した。

## クイックリファレンス

| アンチパターン | 修正 |
|--------------|-----|
| モック要素にアサート | 実際のコンポーネントをテストするかモック解除 |
| プロダクションにテスト専用メソッド | テストユーティリティに移動 |
| 理解せずにモック | 依存関係を先に理解、最小限のモック |
| 不完全なモック | 実際の API を完全に反映 |
| 後付けテスト | TDD — テストファースト |
| 過度に複雑なモック | 統合テストを検討 |

## 危険信号

- `*-mock` テスト ID に対するアサーション
- テストファイルでしか呼ばれないメソッド
- モックセットアップがテストの50%以上
- モックを削除するとテストが失敗
- なぜモックが必要か説明できない
- 「安全のため」にモック

## 結論

**モックは分離のためのツールであり、テスト対象ではない。**

TDD がモックの振る舞いをテストしていることを明らかにしたなら、方向が間違っている。

修正: 実際の振る舞いをテストするか、なぜモックしているのか問い直す。
