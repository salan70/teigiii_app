# 実装計画の作成

## 概要

コードベースの文脈がゼロで、センスも怪しいエンジニアを想定して、包括的な実装計画を書きます。各タスクで知るべきことをすべてドキュメント化してください: どのファイルを触るか、コード、テスト、確認すべきドキュメント、テスト方法。計画全体を一口サイズのタスクとして提供します。DRY。YAGNI。TDD。頻繁なコミット。

スキルのある開発者を想定しますが、ツールセットや問題ドメインについてはほぼ何も知りません。テスト設計にもあまり詳しくないと想定してください。

**開始時に宣言:** 「wf-03-writing-plans スキルを使って実装計画を作成します。」

**コンテキスト:** wf-01-brainstorming スキルが作成した専用の worktree で実行してください。

**計画の保存先:** `doc/plans/YYYY-MM-DD-<feature-name>.md`
- （ユーザーが計画の保存場所を指定している場合はそちらを優先）

## スコープの確認

仕様が複数の独立したサブシステムをカバーしている場合、wf-01-brainstorming でサブプロジェクト仕様に分割されているべきです。されていなければ、サブシステムごとに別々の計画に分けることを提案してください。各計画は単独で動作可能でテスト可能なソフトウェアを生み出すべきです。

## ファイル構成

タスクを定義する前に、作成・変更するファイルと各ファイルの責務を整理してください。ここで分解の決定が確定します。

- 明確な境界とインターフェースを持つ単位に設計する。各ファイルはひとつの明確な責務を持つべき。
- コンテキストに収まるコードの方が的確に推論でき、ファイルが集中的であるほど編集の信頼性が高い。多機能すぎる大きなファイルよりも、小さくて集中的なファイルを優先する。
- 一緒に変更されるファイルは一緒に配置する。技術レイヤーではなく責務で分割する。
- 既存コードベースでは確立されたパターンに従う。コードベースが大きなファイルを使っている場合、一方的に構造を変えない — ただし、変更対象のファイルが扱いにくくなっている場合は、分割を計画に含めるのは合理的。

この構成がタスク分解の基礎になります。各タスクは独立して意味のある自己完結した変更を生み出すべきです。

## 一口サイズのタスク粒度

**各ステップはひとつのアクション（2〜5 分）:**
- 「失敗するテストを書く」— ステップ
- 「実行して失敗を確認」— ステップ
- 「テストを通す最小限のコードを実装」— ステップ
- 「テストを実行して通ることを確認」— ステップ
- 「コミット」— ステップ

## 計画ドキュメントのヘッダー

**すべての計画は必ずこのヘッダーで始めてください:**

```markdown
# [機能名] 実装計画

> **エージェント向け:** 必須サブスキル: superpowers:wf-04-subagent-driven-development（推奨）または superpowers:wf-04-executing-plans を使用して、この計画をタスクごとに実装してください。各ステップは進捗追跡用にチェックボックス (`- [ ]`) 構文を使用しています。

**ゴール:** [何を構築するか 1 文で]

**アーキテクチャ:** [アプローチについて 2〜3 文]

**技術スタック:** [主要な技術/ライブラリ]

---
```

## タスク構造

````markdown
### Task N: [コンポーネント名]

**ファイル:**
- 作成: `exact/path/to/file.py`
- 変更: `exact/path/to/existing.py:123-145`
- テスト: `tests/exact/path/to/test.py`

- [ ] **Step 1: 失敗するテストを書く**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **Step 2: テストを実行して失敗を確認**

実行: `pytest tests/path/test.py::test_name -v`
期待: FAIL（"function not defined"）

- [ ] **Step 3: 最小限の実装を書く**

```python
def function(input):
    return expected
```

- [ ] **Step 4: テストを実行して通ることを確認**

実行: `pytest tests/path/test.py::test_name -v`
期待: PASS

- [ ] **Step 5: コミット**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## 注意事項
- 常に正確なファイルパス
- 計画内に完全なコードを記載（「バリデーションを追加」ではなく）
- 正確なコマンドと期待される出力
- 関連スキルを @ 構文で参照
- DRY、YAGNI、TDD、頻繁なコミット

## 計画レビューループ

計画の完成後:

1. 的確に構成されたレビュー文脈で plan-document-reviewer サブエージェントを 1 つディスパッチ（plan-document-reviewer-prompt.md を参照）— セッション履歴は渡さない。レビュアーを計画に集中させ、思考過程を見せない。
   - 提供するもの: 計画ドキュメントのパス、仕様ドキュメントのパス
2. 問題ありの場合: 問題を修正し、計画全体に対してレビュアーを再ディスパッチ
3. 承認の場合: 実行の引き渡しに進む

**レビューループのガイダンス:**
- 計画を書いたエージェントが修正する（コンテキストが保持されるため）
- ループが 3 回を超えた場合、ユーザーに報告して判断を仰ぐ
- レビュアーは助言的 — フィードバックが不正確だと考える場合は異議を説明する

## 実行の引き渡し

計画を保存した後、実行方法を提示:

**「計画が完成し `doc/plans/<filename>.md` に保存しました。2 つの実行方法があります:**

**1. サブエージェント駆動（推奨）** - タスクごとに新しいサブエージェントをディスパッチ、タスク間にレビュー、高速な反復

**2. インライン実行** - wf-04-executing-plans を使ってこのセッションでタスクを実行、チェックポイント付きバッチ処理

**どちらにしますか？」**

**サブエージェント駆動を選択した場合:**
- **必須サブスキル:** superpowers:wf-04-subagent-driven-development を使用
- タスクごとに新しいサブエージェント + 2 段階レビュー

**インライン実行を選択した場合:**
- **必須サブスキル:** superpowers:wf-04-executing-plans を使用
- チェックポイント付きバッチ処理
