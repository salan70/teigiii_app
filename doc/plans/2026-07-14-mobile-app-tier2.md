# モバイルアプリ Tier 2（初期リリース後の段階投入）統括プラン

> 注記: ディレクトリ再編に伴いパス表記を現行構成へ更新した（#230）。

## 目的

`doc/specs/mobile-app-information-architecture.md` の Tier 2 スコープを、Tier 1 リリース後に機能単位で段階投入する。

本プランは統括用であり、各機能に着手する際は詳細プランを `doc/plans/` に別途作成する。スキーマは事前に作らず、各機能の投入時に Drizzle のマイグレーションで追加する。

## 前提

- Tier 1（`2026-07-14-mobile-app-tier1.md`）のリリースが完了していること
- 各機能の投入順・要否は Tier 1 リリース後の利用状況を見て判断する（本プランの順序は仮）

## スコープ（Tier 2）

情報設計 §0 の Tier 2 に準拠する。

| 機能 | 依存・備考 |
|---|---|
| リアクション 3 種化（いいね・なるほど・おもしろい） | 単独で投入可能。既存いいねは 1 種として引き継ぐ |
| 通知（アプリ内 + プッシュ + ヘッダーのベル） | §14。日次まとめ・種別ごとの設定を含む |
| 定義リクエスト | §11。リクエスト通知は通知基盤に依存。絞り込み「定義リクエストあり」、言葉の作成者修正条件への追加、タイムライン活動表示の再検討を含む |
| グローバル検索「定義」タブ（本文検索） | LIKE 部分一致。単独で投入可能 |
| ブロック | §15。除外箇所が多岐（タイムライン・言葉ページ・検索・一覧・通知） |
| 修正提案・通報の構造化フロー | §16.3。分離した申請フォームと種別 |
| 定義詳細への通知起点の直接遷移 | 通知に依存 |

## 実行手順

1. Tier 1 リリース後、利用状況をもとに投入順を確定する（目安: リアクション 3 種化 → 通知 → 定義リクエスト → 残り）
2. 機能ごとに詳細プランを作成し、スキーマ追加（マイグレーション）→ API → UI の順で実装する
3. 各機能の初回利用時オンボーディング（情報設計 §18.3）を同時に投入する
4. 完了した詳細プランは `doc/plans/done/` へ移動する

## 完了条件

- 上記スコープの各機能について「リリース済み」または「見送り」の判断が記録されている（全機能の実装は必須としない）
- 投入した機能が情報設計ドキュメントと一致している（乖離はドキュメント側を更新して記録）
