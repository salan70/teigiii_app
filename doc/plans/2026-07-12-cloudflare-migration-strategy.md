# Cloudflare 移行 & UI 刷新 戦略

## 目的

- DB を Firestore から RDB（Cloudflare D1）へ移行し、固定費を限りなく 0 に近づける
- 「SNS か辞書か どっちつかず」になっている UI を刷新し、コンセプトに沿った体験に作り直す
- 両者は根本的なデータ設計を共有するため、先に全体方針を確定し、その方針の下で段階的に実行する

### プロダクトコンセプト（判断の基準）

- 自分の言葉で世の中の言葉を定義する
- 言葉の定義の広さ・曖昧さに触れる（他の人の定義に触れる）

## 決定事項

### 1. プロダクトの軸: 辞書型

- 情報の起点を「言葉」に置く。ある言葉を引くと自分の定義と他者の定義が並ぶ体験を主軸とする
- SNS 的要素（タイムライン）は脇役として残す

### 2. タイムライン: フォロータブ + おすすめタブの 2 フィード

- フォロー機能は維持する（`UserFollows` 相当を新スキーマに移植）
- おすすめフィードは「新着 + いいね数等の単純スコアリング」を SQL のオンザフライ計算で実現する。事前計算フィードや ML は導入しない

### 3. データ保全: 完全保全 + big-bang 一斉切替

- 実ユーザー・実投稿が存在するため、全ユーザー・全定義・いいね・フォロー関係を移行する
- 既存の強制アップデート機構（`force_event`）を使い、「旧バージョン強制停止 → メンテナンス中に一括エクスポート/インポート → 新バージョン公開」の一斉切替を行う
- デュアルライト等の段階移行は個人開発では過剰なため採用しない

### 4. Firebase の脱却範囲: データ層のみ

| サービス | 方針 |
|---|---|
| Firestore | **D1 へ移行**（今回の主目的） |
| Storage | **R2 へ移行**（egress 無料・無料枠あり） |
| Auth | **残す**（無料枠が実質無制限。UID をそのまま新 DB の `users.id` に使い、認証移行をゼロにする） |
| Crashlytics / Analytics | **残す**（無料。Cloudflare に代替なし） |
| App Check | **残す**（Workers API の保護に流用） |

### 5. サーバー側スタック

| 要素 | 選定 |
|---|---|
| DB | Cloudflare D1（SQLite） |
| API フレームワーク | Hono（TypeScript） |
| ORM / マイグレーション | Drizzle ORM + drizzle-kit |
| API 形式 | REST + OpenAPI（`@hono/zod-openapi`）。OpenAPI から Dart クライアントを自動生成する |
| 認証検証 | Workers 側で Firebase ID トークンを JWT 検証（公開鍵検証のみ、Admin SDK 不要） |

- D1 は単一リージョン SQLite であり同時書込みに上限があるが、本アプリの規模では問題にならないと判断し受容する
- 現行のリアルタイムリスナー依存は `app_config_repository.dart`（強制アップデート監視）の 1 箇所のみで、起動時ポーリングで代替する

### 6. 進め方: DB 移行を先行、UI は据え置き

1. 新 UI の情報設計（画面マップ・ナビゲーション構造）だけを先に固める
2. それを満たす RDB スキーマ + API を設計する（旧 UI はそのスキーマの部分集合で動作する）
3. 既存 UI の repository 層だけを REST に繋ぎ替え、big-bang でデータ移行する（見た目・挙動は同一のままバックエンドのみ切替）
4. 安定後、API の上で UI を画面単位で段階的に刷新する

採用理由: 変数を 1 つずつ切り替えることで、移行リリースを旧環境との突き合わせで検証できる。Firestore 上に新 UI を作る案（B 案）は repository 層を使い捨てで 2 回書く上に、新 UI が Firestore のクエリ制約に引きずられるため却下。

### 7. リポジトリ構成: モノレポ

- 本リポジトリ直下に `server/` を切り、Workers（API + スキーマ）の TypeScript コードを同居させる
- OpenAPI スキーマ → Dart クライアント生成 → Flutter 側修正を 1 コンテキストで完結させる

### スキーマ設計の指針

- 現行の非正規化フィールド（`Definition` への `word` / `authorName` / `likesCount` 埋め込み、`WordDefinitionRelations`、`UserFollowCounts`）は JOIN / `COUNT` / FK に置き換えて正規化する
- `isPublic`（非公開定義）は新スキーマに持ち込む
- `users.id` は Firebase Auth の UID をそのまま使う

## 実行手順（フェーズ）

各フェーズを issue として起票し、順に実施する。

1. **新 UI の情報設計**: 画面マップとナビゲーション構造を決め、`doc/` に記録する
2. **RDB スキーマ + API 設計**: Drizzle スキーマと OpenAPI 定義を作成する
3. **サーバー実装**: `server/` に Workers + Hono + Drizzle + D1 の API を実装する（dev/prod 環境、Firebase ID トークン検証、App Check 検証を含む）
4. **Flutter repository 層の繋ぎ替え**: OpenAPI から Dart クライアントを生成し、Firestore 依存の repository を REST に置換する（UI は変更しない）
5. **データ移行 & 一斉切替**: Firestore → D1、Storage → R2 の移行スクリプトを作成し、`force_event` による強制停止 → 移行 → 新版公開を実施する
6. **UI 刷新**: フェーズ 1 の情報設計に基づき、画面単位で段階的に刷新する

## 完了条件

- Firestore / Firebase Storage への依存がアプリから消え、データ層が D1 / R2 に完全移行されている
- 既存の全ユーザー・定義・いいね・フォロー関係が新 DB 上で保全されている
- 固定費が 0 円（各サービスの無料枠内）で運用されている
- 辞書型を主軸とした新 UI がリリースされている
