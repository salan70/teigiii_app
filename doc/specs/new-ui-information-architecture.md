## 1. 設計方針

本アプリの中心価値は、自分の考えを言語化し、自分の辞書を育てることである。

他者の定義は、自分との違いを楽しみ、新しい視点を得るための副次的な価値として位置付ける。

情報構造の最上位オブジェクトは「定義投稿」や「ユーザー」ではなく、**言葉**とする。

```
言葉
├─ 自分が投稿した定義
├─ 他者が投稿した定義
├─ 保存
└─ 定義リクエスト
```

定義は、同じユーザーが同じ言葉に複数投稿できる独立したオブジェクトとする。

```
言葉「自由」
├─ Aさんの定義
├─ 哲生さんの定義1
├─ Bさんの定義
└─ 哲生さんの定義2
```

「現在の定義」「代表定義」「過去バージョン」という概念は設けない。

### 言葉の公開性（割り切り）

言葉はグローバルな共有資産であり、**非公開の言葉は存在しない**。非公開定義や下書きだけを書く場合でも、言葉自体は公開登録される。隠せるのは定義本文だけである。

ただし**言葉の登録者は UI 上に一切表示しない**（タイムライン・言葉ページ・みんなの辞書のいずれにも出さない）。登録者は内部的にのみ記録し、作成者修正（§16.2）の判定に使う。これによりセンシティブな言葉への関心が登録者名付きで公開されることを防ぐ。

## 2. 最上位ナビゲーション

下部ナビゲーションは 3 領域とする。ラベルは短縮しない。

```
あなたの辞書 | みんなの辞書 | タイムライン
```

### 起動時の画面

起動時は常に「あなたの辞書」を表示する。条件分岐（初回のみ別画面等）は設けない。

新規ユーザー対策として、辞書が空の場合の「あなたの辞書」は通常の空リストではなく、**最初の定義作成へ誘導する専用の空状態**（言葉検索の入力欄をその場に出す等）として設計する。

## 4. あなたの辞書

### 4.1 概要画面

完成した定義だけでなく、自分と言葉との関係を管理する領域とする。

```
あなたの辞書
定義済みの言葉　42
下書き　　　　　3
保存した言葉　　12
最近書いた定義
────────────────
自由 「……」
仕事 「……」
```

概要画面から移動できる先: 定義済みの言葉 / 下書き / 保存した言葉 / 最近書いた定義 / 新しい定義の作成。

### 4.2 定義済み一覧

定義単位ではなく、**言葉単位**でまとめる。同じ言葉に複数定義があっても一覧には言葉を 1 件だけ表示する。

```
定義済みの言葉
自由　公開 2件・非公開 1件
仕事　公開 1件
```

### 4.3 下書き

- 同じ言葉に複数の下書きを作成できる
- **サーバー保存**とする。スキーマ上は独立テーブルではなく、definitions の状態（`draft` / `public` / `private`）の 1 つとして持つ
- 自動保存は**作成画面から離脱する時のみ**行う（明示保存は別途あり）。入力中の定期保存はしない
- 完全に空の入力は下書きとして作成しない

### 4.4 保存した言葉

保存は単一の機能とする。「あとで読む」「あとで定義する」等には分けない。定義済みかどうかはシステム側で判定して表示できる。

## 5. みんなの辞書

共有されているすべての言葉を網羅的に閲覧する領域。人気順・新着順ではなく**読み順**を基本とする。

### 5.1 並び順

```
あ
├─ 愛
├─ 相性
└─ アイスクリーム
い
├─ 生きる
└─ 意識
```

### 5.2 絞り込み

```
すべて / 定義あり / 定義なし / 定義リクエストあり（Tier 2）
```

定義が 0 件の言葉も通常の言葉と同様に表示する。

### 5.3 言葉の登録

- みんなの辞書に「言葉を登録」の入口を設置する
- 登録前に既存の言葉を検索し、重複候補を強く提示する
- 登録後は、続けて定義を書くかを選択できる

```
「余白」を登録しました
[続けて定義を書く] [完了]
```

## 6. タイムライン

2 タブ構成。初回は「見つける」を表示し、2 回目以降は最後に開いていたタブを復元する。

```
見つける | フォロー中
```

### 6.1 見つける

アプリ全体の新しい活動を、**集約なしの完全な新着順**で表示する。

初期リリースの対象活動:

- 新しい公開定義
- 新しい言葉の登録（登録者は表示しない）

定義リクエストの活動表示は Tier 2 でリクエスト機能を入れる際に再検討する。

おすすめスコアリング（新着 + いいね数等）は初期は導入しない。言葉単位の集約表示・同一ユーザーの連続表示抑制も将来検討とする（時系列フィードの言葉単位集約はページネーションのカーソル整合が壊れるため、活動量が問題になってから設計する）。

### 6.2 フォロー中

フォローしているユーザーの活動を、完全な新着順で個別に表示する（言葉単位で集約しない）。

初期リリースの対象活動:

- **公開定義の投稿のみ**

言葉の登録は登録者非表示のため対象外。定義リクエストは Tier 2。

表示しない活動: リアクション / 言葉の保存 / フォロー操作 / 下書き / 非公開定義 / 公開範囲の切り替え / 編集期限内の本文修正。

## 7. 言葉ページ

本アプリの中心画面。

### 7.1 基本構造

```
自由
じゆう
[定義する] [保存] [リクエスト(Tier 2)]
あなたの定義
────────────────
みんなの定義
────────────────
新着順 | リアクション順
```

### 7.2 主要アクション

「定義する」を主操作として強調し、保存（とリクエスト）は補助操作として常時表示する。

メニューへ格納する操作: 修正を提案（Tier 2）/ 通報。外部共有は実装しない（§17）。

### 7.3 あなたの定義

他者の定義より先に、自分の定義を表示する。確定済み定義と下書きは分離する。

```
あなたの定義 5件
公開 2・非公開 1・下書き 2
最近の確定済み定義
────────────────
定義A
定義B
[すべて見る]
下書き 2件
[続きを書く]
```

初期表示では、最近の確定済み定義を 2〜3 件表示する。「最近」は現在・代表という意味ではなく、表示上の並び順にすぎない。

### 7.4 みんなの定義

**自分の定義は含めない**（他者の公開定義のみ）。自分の定義は「あなたの定義」セクションに集約し、同一画面での二重表示を避ける。

各定義を独立した投稿として同列に表示する。同じユーザーによる複数定義もすべて表示する。

並び順: 新着順 / リアクション数順（全リアクション種の合計）。

## 8. 定義

### 8.1 定義モデル

定義はそれぞれ独立した投稿とする。

```
定義
├─ 対象の言葉（確定後は変更不可）
├─ 投稿者
├─ 本文
├─ 状態（draft / public / private）
├─ 投稿日時
├─ 編集期限
└─ リアクション
```

同じユーザーが同じ言葉へ複数の定義を投稿できる。投稿数に通常の上限は設けず、明らかなスパム・自動投稿だけをバックエンド側で制限する。

### 8.2 文字数

現行実装に準拠する（`definition_for_write.dart` で確認済み）。

| 項目 | 最大文字数 |
|---|---|
| 言葉 | 30 文字 |
| よみ | 50 文字 |
| 定義本文 | 500 文字 |

よみは必須とする。

### 8.3 状態

**下書き**: 他者には表示されない / 無期限で編集可能 / 同じ言葉に複数作成可能 / 明示保存と離脱時自動保存に対応

**公開**: 他者に表示される / 確定後 1 時間だけ本文を編集可能 / 以後も公開・非公開の変更は可能

**非公開**: 本人だけに表示される / 確定後 1 時間だけ本文を編集可能 / 以後も公開・非公開の変更は可能

公開・非公開として確定した定義を下書きへ戻すことはできない。

### 8.4 編集期限

初めて公開または非公開として保存した時刻から **1 時間**とする（現行実装の編集期限に準拠）。

```
finalized_at
↓
editable_until = finalized_at + 1時間
```

- 公開・非公開を切り替えても編集期限は延長しない
- 編集できるのは**本文のみ**。確定後の対象の言葉の変更は不可（現行は可能だが、新モデルでは定義がタイムライン活動・リアクションを持つ独立オブジェクトになるため廃止する）。言葉を間違えた場合は削除して新規投稿する
- 期限後に別の考えを書きたい場合は、同じ言葉に新しい定義を投稿する

### 8.5 新しい定義の作成

- 作成画面では他者の定義を表示しない。自分の過去の定義だけを参考情報として表示できる
- 過去の本文は入力欄へ自動複製しない
- 既存下書きがある場合は作成画面内で静かに案内する（新規作成自体は妨げない）

## 9. 定義詳細

各定義に独立した詳細画面を用意する（Tier 1）。

表示要素: 対象の言葉 / 定義本文 / 投稿者 / 投稿日時 / 公開状態（本人のみ）/ リアクション / 通報 / 削除・公開範囲変更（本人のみ）。

- 対象の言葉ページへ戻る導線を必ず設ける
- 通知からの直接遷移は Tier 2（通知機能と同時）。外部共有からの遷移は実装しない（§17）

## 10. リアクション

- **Tier 1**: 現行パリティの「いいね」1 種のみ
- **Tier 2**: 3 種化（いいね・なるほど・おもしろい）。1 ユーザーは同じ定義に複数種類を付けられるが、同じ種類は 1 回まで

自分の定義にもリアクション可能とし（現行と同じ）、表示件数・並び順へ含める。

リアクション数は本文より小さく控えめに表示する。

コメント・返信機能は設けない。他者の定義に意見を書きたい場合は、同じ言葉に自分の定義を投稿する。

## 11. 定義リクエスト（Tier 2）

- 定義数に関係なく任意の言葉へリクエストできる。意味は「この言葉について、もっと定義を投稿してほしい」
- ユーザーが手動解除するまで継続する（新しい公開定義が追加されても自動解除しない）
- リクエスト中の言葉に定義が追加された場合は 1 日単位で通知をまとめる
- 同じユーザー・同じ言葉につき 1 件

## 12. グローバル検索

すべての最上位画面のヘッダーに検索アイコンを配置する。

```
Tier 1 ヘッダー:
あなたの辞書  [検索] [アバター]
みんなの辞書  [検索]
タイムライン  [検索]
（通知ベルは Tier 2 で追加）
```

検索結果はタブで分ける。初期タブは「言葉」。検索文字列はタブ切り替え後も維持する。

| タブ | 対象 | Tier |
|---|---|---|
| 言葉 | 表記・よみ | 1 |
| 定義 | 定義本文（LIKE 部分一致） | 2 |
| ユーザー | 表示名・ユーザー ID | 1 |

みんなの辞書内にも、表示中の言葉だけを絞り込む検索欄を設ける。

## 13. ユーザープロフィール

プロフィールと公開辞書を一体化する。公開辞書は言葉単位でまとめる。

```
Aさん
自己紹介
[フォロー]
公開している定義 42 / フォロー 31 / フォロワー 280
Aさんの辞書
────────────────
自由　3件
仕事　1件
```

表示する数値: 公開定義数 / フォロー数 / フォロワー数。
表示しない数値: 獲得リアクション総数 / 人気順位 / 平均リアクション数。

自分のプロフィール・設定へは「あなたの辞書」右上のアバターから移動する。

## 14. 通知（Tier 2）

通知画面は下部ナビゲーションに置かず、上部のベルアイコンから開く。

### 14.1 アプリ内通知

対象: 自分の定義へのリアクション / フォローされた / 自分が登録した言葉への定義追加 / リクエスト中の言葉への定義追加 / 保存した言葉への定義追加（初期状態オフ）。

同じ定義・同じ言葉に対する通知は対象単位でまとめる。

### 14.2 プッシュ通知

初期状態でプッシュ: フォローされた / リクエスト中の言葉への定義追加。
アプリ内のみ: リアクション / 登録した言葉への定義追加 / 保存した言葉への定義追加。

通知種別ごとに設定からオン・オフできる。

## 15. フォロー・ミュート・ブロック

- **フォロー**（Tier 1）: フォロー中タイムラインにそのユーザーの公開活動を表示する
- **ミュート**（Tier 1・現行パリティ）: 相手の活動を自分のタイムラインから除外。相手には通知されない
- **ブロック**（Tier 2）: 相互作用を遮断し、相手のコンテンツを完全に非表示。タイムライン / 言葉ページ / 検索結果 / リアクション一覧 / フォロー一覧 / 通知から除外する

## 16. 言葉の管理

### 16.1 言葉の同一性

同じ表記の言葉は、指す対象が異なっても同じ言葉として扱う。意味・語義ごとに分割しない。

### 16.2 作成後の修正（Tier 1）

言葉の作成者は、次の条件を満たす場合だけ表記・よみを直接修正できる。

- 作成後 **1 時間**以内（定義の編集期限と統一）
- 他ユーザーによる操作（**定義投稿・保存**）がまだない
  - Tier 2 で定義リクエスト導入後は、リクエストも「他ユーザーによる操作」に加える

条件を満たさない場合は「修正を提案」（Tier 2）から申請する。Tier 1 の間は現行の通報相当の導線で代替する。

### 16.3 修正提案と通報（構造化フローは Tier 2）

言葉ページでは次を分離する。

- 修正を提案: 表記 / よみ / 重複 / 明らかな登録ミス
- 通報: 誹謗中傷 / 個人情報 / 権利侵害 / なりすまし / スパム / 違法・有害な内容

申請後は送信完了だけを表示し、ユーザー向け履歴画面は作らない。

## 17. 外部共有 — 実装しない

外部共有（ディープリンク、`/words/{wordId}` 等の URL、Web ランディング）は**初期の情報設計に含めない**。将来拡張候補（§20）とする。

理由: 中心体験（辞書を育てる・違いを楽しむ）に必須ではなく、ドメイン・Universal Links / App Links・未インストール時の受け皿などインフラ作業が大きい。スキーマへの影響はほぼないため、必要になった時点で追加できる。

## 18. 認証と初回利用

### 18.1 現在

匿名認証を自動実行し、すべての機能を利用可能にする。ログイン前・ログイン後という画面分岐は設けない。

```
初回起動 → 匿名認証 → 簡単な導入 → あなたの辞書
```

### 18.2 将来

Apple・Google 認証を追加する。匿名アカウントを置き換えるのではなく、既存の匿名ユーザーへ認証方法をリンクし、データを維持する。一定の利用実績（例: 定義 3 件、利用開始 7 日）でアカウント保護を案内する。

### 18.3 オンボーディング

初回は 1 画面だけ簡潔に説明する。

```
言葉を、自分の言葉で残す辞書です
[はじめる]
```

各機能の説明は初回利用時に段階的に表示する（対象機能の Tier に従う）。

- 最初の定義作成時: 公開・非公開・下書き（Tier 1）
- 最初のリクエスト時: 継続通知（Tier 2）
- 最初のリアクション時: 複数種類を付与可能（Tier 2）

## 19. 削除

論理削除の目的は**運用上の安全弁**である（誤削除時の手動復元、通報・不正調査の証跡）。ユーザー向けの「削除の取り消し」機能は作らない。

### 定義削除

ユーザー画面上では即時に削除され、内部では **30 日間**論理削除した後、完全削除する。

削除後: 言葉ページ / プロフィール / タイムラインから非表示。リアクションも非表示。通知から開いた場合は削除済みと表示（Tier 2）。

### アカウント削除

ユーザーから見える削除は即時。内部では 30 日間論理削除した後、完全削除する。

削除対象: 公開定義 / 非公開定義 / 下書き / リアクション / 保存 / 定義リクエスト / フォロー関係 / 通知 / プロフィール。公開定義を匿名化して残すことはしない。

物理削除のバッチ実装（Cron Triggers 等）はフェーズ 2〜3 で設計する。

## 20. 初期の情報設計に含めないもの（将来拡張候補）

## 21. 最終ナビゲーション概要

```
下部ナビゲーション
├─ あなたの辞書（起動画面・固定）
├─ みんなの辞書
└─ タイムライン
   ├─ 見つける
   └─ フォロー中

共通ヘッダー
├─ グローバル検索
└─ 通知（Tier 2）

あなたの辞書のみ
└─ アバター → 公開プロフィール / プロフィール編集 / 設定

主要作成導線
あなたの辞書 → 定義を書く → 言葉を検索 → 存在しなければ言葉を登録 → 定義を書く
みんなの辞書 → 言葉を登録 → 続けて定義を書くか選択
言葉ページ → この言葉を定義する
```
