# 体系的デバッグ

## 概要

場当たりな修正は時間を浪費し、新たなバグを生む。応急処置は根本的な問題を覆い隠す。

**基本原則:** 修正を試みる前に必ず根本原因を特定する。症状の修正は失敗である。

**このプロセスの文言に違反することは、デバッグの精神に違反することである。**

## 鉄の掟

```
根本原因の調査なしに修正してはならない
```

フェーズ 1 を完了していなければ、修正を提案できない。

## いつ使うか

あらゆる技術的問題に使用する:
- テスト失敗
- 本番のバグ
- 予期しない振る舞い
- パフォーマンス問題
- ビルド失敗
- 統合の問題

**特に以下の場合に使用:**
- 時間的プレッシャーがあるとき（緊急時は推測しがち）
- 「ちょっとした修正」が明白に見えるとき
- 既に複数の修正を試したとき
- 前回の修正が効かなかったとき
- 問題を完全に理解していないとき

**スキップしないこと:**
- 問題がシンプルに見えるとき（シンプルなバグにも根本原因はある）
- 急いでいるとき（急ぐとやり直しが確定する）
- マネージャーが今すぐ修正しろと言っているとき（体系的な方が試行錯誤より速い）

## 4つのフェーズ

各フェーズを完了してから次に進むこと。

### フェーズ 1: 根本原因の調査

**いかなる修正を試みる前に:**

1. **エラーメッセージを注意深く読む**
   - エラーや警告を読み飛ばさない
   - 正確な解決策が書かれていることが多い
   - スタックトレースを最後まで読む
   - 行番号、ファイルパス、エラーコードを記録

2. **安定して再現する**
   - 確実にトリガーできるか？
   - 正確な手順は？
   - 毎回起きるか？
   - 再現できない場合 → より多くのデータを集める、推測しない

3. **最近の変更を確認する**
   - これを引き起こし得る変更は何か？
   - git diff、最近のコミット
   - 新しい依存関係、設定変更
   - 環境の差異

4. **マルチコンポーネントシステムでのエビデンス収集**

   **システムに複数のコンポーネントがある場合（CI → ビルド → 署名、API → サービス → DB）:**

   **修正を提案する前に、診断用のインストルメンテーションを追加:**
   ```
   各コンポーネント境界について:
     - コンポーネントに入るデータをログ
     - コンポーネントから出るデータをログ
     - 環境/設定の伝播を検証
     - 各レイヤーの状態を確認

   一度実行して、どこで壊れるかを示すエビデンスを収集
   その後エビデンスを分析して故障コンポーネントを特定
   そしてそのコンポーネントを調査
   ```

   **例（多層システム）:**
   ```bash
   # レイヤー 1: ワークフロー
   echo "=== ワークフローで利用可能なシークレット: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # レイヤー 2: ビルドスクリプト
   echo "=== ビルドスクリプトの環境変数: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # レイヤー 3: 署名スクリプト
   echo "=== キーチェーンの状態: ==="
   security list-keychains
   security find-identity -v

   # レイヤー 4: 実際の署名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **これにより判明する:** どのレイヤーが失敗しているか（シークレット → ワークフロー ✓、ワークフロー → ビルド ✗）

5. **データフローをトレースする**

   **エラーがコールスタックの深い位置にある場合:**

   このディレクトリの `root-cause-tracing.md` に完全な逆トレース技法がある。

   **要約:**
   - 不正な値はどこで発生しているか？
   - 不正な値を渡して呼び出したのは何か？
   - ソースを見つけるまでトレースを続ける
   - 症状ではなくソースで修正する

### フェーズ 2: パターン分析

**修正前にパターンを見つける:**

1. **動作する例を見つける**
   - 同じコードベースの類似する動作コードを探す
   - 壊れているものと似ていて動作しているものは何か？

2. **リファレンスと比較する**
   - パターンを実装しているなら、リファレンス実装を完全に読む
   - 流し読みしない — 全行を読む
   - 適用する前にパターンを完全に理解する

3. **差異を特定する**
   - 動作するものと壊れているものの違いは何か？
   - どんなに小さくても、すべての違いを列挙する
   - 「それは関係ない」と仮定しない

4. **依存関係を理解する**
   - これには他にどのコンポーネントが必要か？
   - どの設定、構成、環境が必要か？
   - どんな前提があるか？

### フェーズ 3: 仮説と検証

**科学的方法:**

1. **単一の仮説を立てる**
   - 明確に述べる:「Y という理由で X が根本原因だと思う」
   - 書き留める
   - 曖昧ではなく具体的に

2. **最小限のテスト**
   - 仮説を検証するための最小限の変更を行う
   - 一度に1つの変数
   - 複数を同時に修正しない

3. **続行前に検証する**
   - うまくいった？ はい → フェーズ 4
   - うまくいかなかった？ 新しい仮説を立てる
   - 追加の修正を重ねない

4. **わからないとき**
   - 「X がわからない」と言う
   - 知ったかぶりをしない
   - 助けを求める
   - さらに調査する

### フェーズ 4: 実装

**症状ではなく根本原因を修正する:**

1. **失敗するテストケースを作成する**
   - 最もシンプルな再現
   - 可能なら自動テスト
   - フレームワークがなければ使い捨てテストスクリプト
   - 修正前に必ず作成
   - 適切な失敗テストの書き方は `superpowers:test-driven-development` スキルを使用

2. **単一の修正を実装する**
   - 特定した根本原因に対処する
   - 一度に1つの変更
   - 「ついでに」の改善をしない
   - リファクタリングをバンドルしない

3. **修正を検証する**
   - テストがパスするようになったか？
   - 他のテストは壊れていないか？
   - 問題は実際に解決したか？

4. **修正がうまくいかない場合**
   - 止まる
   - 数える: 何回修正を試みたか？
   - 3回未満: フェーズ 1 に戻り、新しい情報で再分析
   - **3回以上: 止まってアーキテクチャを疑う（下記ステップ 5）**
   - アーキテクチャの議論なしに修正 #4 を試みない

5. **3回以上の修正が失敗した場合: アーキテクチャを疑う**

   **アーキテクチャ上の問題を示すパターン:**
   - 各修正が異なる場所で新たな共有状態/結合/問題を明らかにする
   - 修正に「大規模リファクタリング」が必要
   - 各修正が別の場所で新たな症状を引き起こす

   **基本に立ち返って疑問を呈する:**
   - このパターンは本質的に健全か？
   - 惰性で続けていないか？
   - 症状の修正を続けるより、アーキテクチャをリファクタすべきか？

   **さらなる修正を試みる前に人間のパートナーと議論する**

   これは失敗した仮説ではない — アーキテクチャの問題である。

## 危険信号 - 止まってプロセスに従う

以下のように考えている自分に気づいたら:
- 「今は応急処置で、後で調査する」
- 「とりあえず X を変えてみよう」
- 「複数の変更を加えてテストを実行」
- 「テストはスキップして手動で確認」
- 「たぶん X だから修正しよう」
- 「完全には理解していないけどこれでうまくいくかも」
- 「パターンでは X と書いてあるけど別のやり方で」
- 「主な問題はこれ: [調査なしに修正をリストアップ]」
- データフローをトレースする前に解決策を提案
- **「もう1回だけ修正を試みる」（既に2回以上試した場合）**
- **各修正が別の場所で新たな問題を明らかにする**

**これらはすべて次を意味する: 止まる。フェーズ 1 に戻る。**

**3回以上修正が失敗した場合:** アーキテクチャを疑う（フェーズ 4.5 を参照）

## やり方を間違えているサイン

**以下のリダイレクションに注意:**
- 「それは起きていないのか？」 — 確認せずに仮定した
- 「それで見えるようになるか...？」 — エビデンス収集を追加すべきだった
- 「推測をやめろ」 — 理解せずに修正を提案している
- 「じっくり考え直せ」 — 症状ではなく基本を問え
- 「行き詰まったのか？」（苛立ち） — アプローチが機能していない

**これらを見たら:** 止まる。フェーズ 1 に戻る。

## よくある合理化

| 言い訳 | 現実 |
|--------|---------|
| 「問題がシンプルだからプロセスは不要」 | シンプルな問題にも根本原因はある。プロセスはシンプルなバグなら速い。 |
| 「緊急だからプロセスの時間がない」 | 体系的デバッグは試行錯誤より速い。 |
| 「まずこれを試してから調査する」 | 最初の修正がパターンを決める。最初から正しくやる。 |
| 「修正が効くか確認してからテストを書く」 | テストされていない修正は定着しない。テストが先に証明する。 |
| 「一度に複数修正すれば時間節約」 | 何が効いたか分離できない。新たなバグの原因に。 |
| 「リファレンスが長すぎるからパターンを適応する」 | 部分的な理解はバグを保証する。完全に読む。 |
| 「問題が見えたから修正する」 | 症状を見る ≠ 根本原因を理解。 |
| 「もう1回修正を試みる」（2回以上の失敗後） | 3回以上の失敗 = アーキテクチャの問題。パターンを疑え、また修正するな。 |

## クイックリファレンス

| フェーズ | 主要活動 | 成功基準 |
|-------|---------------|------------------|
| **1. 根本原因** | エラーを読む、再現、変更確認、エビデンス収集 | 何が起きて、なぜかを理解 |
| **2. パターン** | 動作例を見つけ、比較 | 差異を特定 |
| **3. 仮説** | 理論を立て、最小限のテスト | 確認または新しい仮説 |
| **4. 実装** | テスト作成、修正、検証 | バグ解消、テストパス |

## プロセスが「根本原因なし」を明らかにしたとき

体系的な調査の結果、問題が本当に環境依存、タイミング依存、または外部要因と判明した場合:

1. プロセスは完了している
2. 調査した内容を文書化する
3. 適切なハンドリングを実装する（リトライ、タイムアウト、エラーメッセージ）
4. 将来の調査のためにモニタリング/ログを追加する

**ただし:** 「根本原因なし」の95%は調査が不完全。

## 補助テクニック

これらのテクニックは体系的デバッグの一部であり、このディレクトリにある:

- **`root-cause-tracing.md`** — コールスタックを逆方向にトレースしてバグの最初のトリガーを見つける
- **`defense-in-depth.md`** — 根本原因を見つけた後、複数レイヤーにバリデーションを追加する
- **`condition-based-waiting.md`** — 任意のタイムアウトを条件ポーリングに置き換える

**関連スキル:**
- **superpowers:test-driven-development** — 失敗するテストケースの作成（フェーズ 4、ステップ 1）

## 実績

デバッグセッションから:
- 体系的アプローチ: 15-30分で修正
- 場当たり修正アプローチ: 2-3時間の試行錯誤
- 初回修正成功率: 95% vs 40%
- 新たなバグの導入: ほぼゼロ vs 頻発
