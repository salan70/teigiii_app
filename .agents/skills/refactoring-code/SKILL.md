# コードのリファクタリング

## 概要

リファクタリングは、振る舞いを変えずにコード構造を改善する。すべてのリファクタリングは TDD のセーフティネットに従う: まずテストで振る舞いをカバーし、その上で安心して構造を変更する。

**開始時の宣言:** 「refactoring-code スキルを使用して、コードを安全にリストラクチャリングします。」

## 原則

- **振る舞いの保持は絶対条件。** リファクタリング対象の振る舞いをテストがカバーしていなければ、先にテストを追加する。
- **小さなステップ、頻繁な検証。** 各リファクタリング操作は独立して検証可能であるべき。
- **一度に一つの関心事。** リファクタリングに機能追加やバグ修正を混ぜない。

## 分析

コードに触れる前に、対象を理解する:

- 問題の特定: 複雑さ、重複、低い凝集度、不明瞭な命名、密結合
- リファクタリングの目標定義: 具体的に「より良い」とはどういう状態か
- 変更スコープの把握: 影響を受けるファイルと関数
- テストカバレッジの評価: 影響を受ける振る舞いはテストでカバーされているか？

## テストのセーフティネット

**必須サブスキル:** TDD サイクルには `test-driven-development` を使用する。

- 既存テストを実行してパスすることを確認する（グリーンベースライン）
- リファクタリングスコープに対してカバレッジが不十分な場合は、先に特性テスト（characterization test）を追加する
- これらのテストは現在の振る舞いをロックインする — リファクタリングの前後で必ずパスしなければならない

## 承認ゲート

変更を行う前に、リファクタリング計画をユーザーに提示する:

- どのような問題に対処するか
- 目標とする構造はどのようなものか
- どのファイルをどの順序で変更するか
- 振る舞いの保持をどのように検証するか

ファイルの編集前にユーザーの明示的な承認を待つ。

## 実行

リファクタリング操作をインクリメンタルに適用する:

- 一度に一つの構造変更を行う
- 各変更後にテストを実行して振る舞いが保持されていることを確認する
- テストが失敗した場合は、直前の変更を元に戻して再評価する
- 予期しない問題や判断は作業ログに記録する

## 検証

**必須:** 完了を宣言する前に、プロジェクトの検証コマンドを実行してエビデンスを示す。

以下のすべてを確認する:

- すべてのテストがパスする（ベースラインと同じ件数、同じ結果）
- リファクタリングの目標が達成されている
- 振る舞いの変更が導入されていない
- スコープクリープなし — 計画されたリファクタリングのみが適用されている
- lint とフォーマットチェックがパスする

## 完了

- 作業ログに振り返りを記録する
- 改善提案を少なくとも 1 つ記録する（ない場合はその理由を述べる）
- 変更をコミットする
- ユーザーに報告する: 何が変わったか、何が改善されたか、検証のエビデンス
