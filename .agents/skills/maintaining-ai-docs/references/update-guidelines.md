# 更新ガイドライン

## 基本原則

コンテキストウィンドウは貴重なリソース。すべての行が存在する価値を持たなければならない。

## 書くべきもの

### 1. コマンド＆ワークフロー

```markdown
## ビルド

`npm run build:prod` — 最適化されたプロダクションビルド
`npm run build:dev` — 高速開発ビルド（ミニファイなし）
```

理由: 将来のセッションがこれらを再発見する手間を省く。

### 2. 非自明なパターンと注意点

```markdown
## 注意点

- テストは `--runInBand` で実行すること（テスト間で DB 状態を共有するため）
- `yarn.lock` が権威ある情報源。依存関係の問題時は `node_modules` を削除して再インストール
```

理由: 繰り返しのデバッグサイクルを防ぐ。

### 3. モジュール間の依存関係

```markdown
## 依存関係

`auth` モジュールは先に `crypto` の初期化が必要。
`src/bootstrap.ts` での import 順序に注意。
```

理由: コードだけからは分からないアーキテクチャ上の知識。

### 4. 実証済みのテストアプローチ

```markdown
## テスト

API エンドポイント: `supertest` + `tests/setup.ts` のヘルパーを使用
モック: `tests/factories/` のファクトリ関数を使用（インラインモック禁止）
```

理由: 実証済みのパターンを確立する。

### 5. 設定の癖

```markdown
## 設定

- `NEXT_PUBLIC_*` 変数はランタイムではなくビルド時に設定が必要
- Redis 接続には IPv6 用の `?family=0` サフィックスが必要
```

理由: 環境固有の知識。

## 書くべきでないもの

### 1. コードから自明な情報

悪い例:
```markdown
`UserService` クラスはユーザー操作を処理する。
```
クラス名がそれを既に示している。

### 2. 一般的なベストプラクティス

悪い例:
```markdown
新機能にはテストを書くこと。
意味のある変数名を使うこと。
```
プロジェクトに固有でない。

### 3. 一度きりの修正

悪い例:
```markdown
コミット abc123 でログインボタンのバグを修正した。
```
再発しない。ファイルを膨らませるだけ。

### 4. 冗長な説明

悪い例:
```markdown
認証システムは JWT トークンを使用している。JWT（JSON Web Tokens）は
RFC 7519 で定義されたオープンスタンダードで...
```

良い例:
```markdown
認証: JWT（HS256）、`Authorization: Bearer <token>` ヘッダー。
```

## 検証チェックリスト

更新を確定する前に確認する:

- [ ] プロジェクト固有の情報である
- [ ] 一般的なアドバイスやコードから自明な情報ではない
- [ ] コマンドは動作確認済み
- [ ] ファイルパスは正確
- [ ] 新しいセッションにとって有用
- [ ] 可能な限り簡潔な表現になっている
